# Which features earn their place

**27 August 2026.** A Kano classification of the sixteen staff screens, and the
minimum viable core underneath them, grounded in what production actually holds
rather than in what the backlog remembers.

**On "MVC":** the task said Kano + MVC without defining it, and nothing in the
repo does. I have read it as **minimum viable core** — the smallest set of
screens that still constitutes a usable shop system, with everything outside it
required to justify itself. If it was meant as something else, the Kano half
stands on its own and the second half is re-runnable against a different
definition.

---

## The caveat that governs everything below

> keep in mind - this system is on testing mode - not yet the ONLY way he uses
> his shop - he wants to migrate slowly till he gets used to each tab, so he's
> using partly and looking for loopoholes etc
> — Shloime, 27 August

**An empty table is not an unwanted feature.** Repairs holds zero rows and the
repair bench is one of the shop's daily trades; what that zero means is "not
migrated yet", not "not needed". Any analysis that reads row counts as demand
would recommend deleting the shop.

So usage evidence is used here in one direction only: **high usage proves a
feature is load-bearing. Low usage proves nothing.** Everything at zero is
classified on the business, not the data, and marked as such.

## Kano classification

Kano asks two questions about each feature — how the user feels when it is
present, and how they feel when it is absent — and the interesting categories
are the ones where those answers are not symmetrical.

### Must-be — absence is a crisis, presence is invisible

Nobody thanks a shop system for these. They are why it is a system.

| Feature | Evidence |
| --- | --- |
| **Customers** | 571 rows; every other table joins to it |
| **Wallet / ledger** | 791 entries, 138 this week. Append-only, and the money bugs this session were all *here* |
| **Phone Rentals** | The trade. 12 rows because migration started this week |
| **SIM Plans** | 797 rows — the largest single thing the shop manages |
| **Settings** | 44 keys. Every price in the business |

Kano's point about must-bes: **investment here buys no delight, and neglect
here is fatal.** That is exactly the shape of this session — the £90, the
uncharged VN, the missing payment method. Nobody will praise the system for
adding money up correctly; getting it wrong once costs more trust than every
delighter combined.

### One-dimensional — more is straightforwardly better

Satisfaction tracks the amount. These are where effort converts linearly.

- **Tasks / the sweep** — 554 rows, 170 raised this week. The single busiest
  surface in the app. Also the most fragile: every false alarm this session
  (the pool flag on a fetched phone, "overdue" the morning after landing) was
  here, and each one erodes the whole queue. More *correct* tasks is better;
  more tasks is not.
- **Tickets & Flights** — 404 bookings, 190 passengers.
- **Carrier Mail** — 462 parsed messages doing work nobody has to do by hand.
- **Confirm Data** — one of Shloime's six findings was that he *couldn't*
  confirm. That is a one-dimensional feature failing at zero.

### Attractive — absent unnoticed, present remembered

The delighters, and the evidence for them is anecdotal by nature.

- **The discount memory.** "at opening a new rental for a customer that had
  already 5 in once, it knew to apply the discount for the 6th … thats
  excellent that it remembered." The one unprompted piece of praise in his test.
  Textbook attractive: he would not have asked for it, and it landed.
- **The in-app contact tools.** Twelve converters on a PC collapse to two
  pages that need no internet.
- **The receipt that draws the hire as a calendar** with the free days shaded —
  the shop showing its working on the number customers are most suspicious of.
- **Scan IMEI, out or back.**

### Indifferent — built, and nothing turns on it

Judged on the business rather than the row count, per the caveat.

- **Kol Torah** (6 tables, all zero). A recently acquired business that has
  never been scoped — "still needs a short scoping session" in PHASE-2-NOTES
  since 16 July. This is not a feature at zero because it is unloved; it is a
  feature built ahead of knowing what it should do.
- **Purchase orders, supplier returns, goods-in** (1 row between them). Retail
  machinery for a shop whose stock is 15 items.

### Reverse — the presence itself is the problem

The category everybody forgets, and the most valuable one here.

- **A task that fires on the ordinary case.** Not a missing feature — a present
  one doing harm. "a task saying it is trains people to ignore tasks." Three
  were fixed this session and the fix in each case was to raise *fewer*.
- **Sixty `zz_snapshot_*` / `undo_*` tables.** Migration debris, several larger
  than the live table they shadow: `undo_20260806_links` holds 1,242 rows
  against `lines`' 34, and `zz_snapshot_sims_20260729` holds 840 against 797.
  They exist because CLAUDE.md requires an undo snapshot before a bulk write,
  which is right — but nothing ever retires them, so the schema now reads as
  mostly wreckage to anyone opening it. **Recommend a retention rule**: keep
  snapshots 30 days, then drop, with the drop recorded.

## The minimum viable core

If the shop had to run on the least that is genuinely a system:

```
Customers ─┬─ Phone Rentals ─┐
           ├─ SIM Plans ─────┼─ Wallet (ledger)
           └─ Tickets ───────┘        │
                                   Settings
```

**Six screens.** Customers because everything joins to it; three because they
are the trade; the ledger because money that is not recorded did not happen;
Settings because every price lives there and the alternative is typing prices
at the counter.

Two things that are *not* in the core but should ship with it anyway, and the
distinction matters:

- **Tasks** is not load-bearing — the shop ran without it. It is what makes the
  other six safe to trust, because it is how the system says something needs
  doing rather than waiting to be asked. Include it, but hold it to the
  "reverse" bar above.
- **The manual** is not a feature at all. It is the thing that makes a system a
  person can be handed. `test/manual.test.mjs` failing the gate when a screen
  changes is the mechanism, and it has caught real drift.

Everything else — Repairs, Shop, Online & Print, Virtual Numbers, Kol Torah,
Confirm Data, Carrier Mail, Messages — is real work that earns its place *when
its trade is migrated*, and not before. The order to migrate them in should be
the order Shloime meets them at the counter, which is his call and not a
data question.

## Two findings turned up on the way

**The flights import stamped ledger rows with the travel date.** All 422
`[flights-sheet]` entries carry a `created_at` of when the customer *flies*,
not when the booking was taken — spread from Feb 2025 to Nov 2026, with **15
rows totalling £3,573 dated in the future.** `pages/api/cashup.js` selects the
day's ledger on `created_at`, so those charges will surface in Z-reports on
days when nothing happened, and historical days show charges never taken then.

Blast radius, stated precisely: these are `booking` charges — negative, and
with no method — so they move the day's *charged* line and **not** expected
cash, which counts only `method = 'cash'` positives. Wrong, but not a till
discrepancy. The ledger is append-only with a mutation trigger, so nothing here
can be quietly rewritten; it needs a decision.

**Sixty snapshot tables and no retention rule.** Above, under Reverse.

## What I would not do with this document

Delete anything on the strength of a zero. The caveat at the top is the whole
finding: this system is being migrated a tab at a time by one person who is
still checking whether it can be trusted, and the row counts measure *how far
he has got*, not what he wants.
